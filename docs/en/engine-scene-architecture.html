Engine / Scene Architecture

The current runtime lives in the public facade package emadurandal/rhodonite/app. The older prototype and phase-plan text is obsolete; examples now use the facade runtime directly.

Runtime Ownership

flowchart TB E[Engine] --> GC[GPUContext] E --> T[TimeState] E --> PH[Phase handlers and groups] E --> SF[Surface list] E --> S[Scene list] SF --> SI[surface-local InputState] SF --> SS[SurfaceState] SF --> RT[RenderTargetResources] S --> W[World] S --> SR[SystemRunner] E --> R[Renderer] R[Renderer] --> GPU[device-wide GPU resources] RT --> TG[surface-sized target resources] R --> S W --> ECS[ECS data and builtin blobs]
TypeResponsibility
EngineOwns GPU context, the standard renderer, render target resources, scenes, surfaces, time, input, phase groups, and on-demand render state.
SceneRuntime scene with one World, one SystemRunner, a main camera, and enabled/visible flags.
WorldECS storage only; it does not own engine lifecycle or GPU resources.
RendererOwns device-wide GPU resources, explicit pipeline layouts, format-keyed pipelines, mesh/material/instance tables, scene renderable extraction, and draw calls.
RenderTargetResourcesOwns surface-local render target state such as color format, extent, and depth attachments.
FrameStatePasses delta, frame index, elapsed time, surface snapshot, and optional surface input to phases and systems.

Phase Groups

flowchart TD A["rhodonite/frame_begin"] --> A1["rhodonite/surface"] A1 --> A2["rhodonite/input"] A2 --> B["rhodonite/fixed_step 0..max_fixed_steps_per_frame"] B --> B1["rhodonite/fixed_update"] B1 --> B2["rhodonite/fixed_post_update"] B2 --> C["rhodonite/render_frame"] C --> C1["rhodonite/update"] C1 --> C2["rhodonite/post_update"] C2 --> C3["rhodonite/render_extract"] C3 --> C4["rhodonite/render_prepare"] C4 --> C5["rhodonite/render"] C5 --> C6["rhodonite/present"]

Engine::run_frame(delta_seconds) runs frame-begin, fixed-step, and render-frame groups in the standard order. Each phase runs before-system handlers, scene systems, and after-system handlers.

  • phase_startup() and phase_shutdown() are one-shot phases, not group members.
  • Custom phase group/order edits are performed during Engine::initialize() startup handlers.
  • Engine::add_phase_handler can take a registration key; handlers with the same phase, slot, and key are deduplicated.
  • Use Engine::on_scene_update / Engine::on_scene_render (TypeScript: Engine.onSceneUpdate / Engine.onSceneRender) for common scene-scoped callbacks. They hide the standard update/render phases, use the standard slots, target only matching multi-surface frames, and apply the scene enabled/visible checks. Engine::on_frame_update / Engine::on_frame_render (TypeScript: Engine.onFrameUpdate / Engine.onFrameRender) are the frame-wide variants; use Engine::add_phase_handler only when custom phases or slots are needed.
  • Scenes implicitly declare the standard transform/camera runtime integration once a main camera is assigned; the scene uses the builtin orbit/home/lens component ids. MoonBit samples call Scene::use_common_runtime, and TypeScript samples call Scene.useCommonRuntime, only when boolean flags need to change optional standard systems such as transform propagation or orbit camera blob sync. Engine::initialize() and scene-only prepare_render_state reflect that declaration into common scene systems, and engine-owned scenes also get orbit-camera input handlers. In TypeScript, the default transform propagation calls world.updateGlobalTransformsFromTransforms() when the scene world exposes it; custom worlds can pass propagateTransforms, and samples can disable propagation with transformPropagation: false. Binding a scene with Engine::set_surface_scene / Engine.setSurfaceScene also installs any declared orbit-camera input handler for that scene.
  • Scene-only or offscreen rendering code can call Scene::prepare_render_state to run update, post_update, and render_extract once without spelling out each phase.
  • When a surface is suspended, update phases still run and render extraction/prepare/render/present are skipped.
  • In on-demand mode, no frame runs while the engine is clean; visible state changes must call request_render.

Surface Model

Single-surface code updates the current snapshot and render target resources through set_surface_active and set_surface_suspended. Multi-surface code uses add_surface, add_surface_for_scene, set_surface_scene, surface_input, and run_multi_surface_frame. Every surface has surface-local input and render target resources.

flowchart LR P[Platform event loop] --> E[Engine] E --> S1[Surface A: canvas/window/input] E --> S2[Surface B: canvas/window/input] S1 --> Scene1[Scene A systems and render] S2 --> Scene2[Scene B systems and render]

Pointer events from canvas/window A do not affect the camera/controller owned by canvas/window B.

Rendering

Engine owns the standard Renderer, and scenes provide the ECS data that renderer paths consume. Renderer, Renderable, resource registration, and draw path details are covered in Rendering Architecture.

PlatformOptions has interactive, render_loop, interactive_on_demand, render_on_demand, and single_frame. Browser start_platform / startPlatform are async; in single_frame mode they return after the submitted GPU work for that one frame has completed.

Sample Layout

Samples now consistently collect sample-local GPU, pipeline, scene, and animation state in a type named DemoState. Platform setup creates the demo state and connects it to the engine with register_engine_handlers(engine, demo_state). ECS samples use Scene as the render source, while low-level samples such as basic triangle use the main scene only as the engine execution boundary.
