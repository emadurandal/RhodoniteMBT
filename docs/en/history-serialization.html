History Serialization

This document defines the persistence boundary for WorldHistory export/import work. The current implementation exposes an in-memory archive model and a TypeScript JSON archive helper for editor/session persistence.

Status

  • WorldHistory::export_undo_stack(world) and WorldHistory::export_redo_stack(world) return an in-memory archive when all retained records are eligible for serialization.
  • WorldHistory::import_undo_stack(world, archive) and WorldHistory::import_redo_stack(world, archive) validate and replace the target stack from that archive without mutating the world.
  • WorldHistory::validate_import_undo_stack(world, archive) and WorldHistory::validate_import_redo_stack(world, archive) return dry-run import validation reports with record and delta locations.
  • The TypeScript wrapper exposes exportUndoStack, exportRedoStack, importUndoStack, importRedoStack, validateImportUndoStack, and validateImportRedoStack. Payload bytes are copied to Uint8Array on export, and plain object archives can be rehydrated on import.
  • The TypeScript npm surface also exposes encodeHistoryExportJson and decodeHistoryExportJson for the JSON archive string format.
  • Import/export and JSON archive encoding use format_version = 1. The JSON field names and payload encoding are covered by v1 golden fixtures and are treated as the compatibility surface. MoonBit core still exposes the in-memory object model only; JSON encoding is implemented in TypeScript.
  • undo_summary and redo_summary are diagnostic views for retained in-memory records. They are not a serialized history archive or compatibility format.
  • MoonBit enum layout, object layout, and internal variant names are not a stable file ABI.
  • The serialized form is for editor/session persistence, not for replaying arbitrary runtime simulation or GPU resource state.

Record Shape

A v1 history archive stores undo and redo stacks as ordered records. Each record contains a label, record-level metadata, and ordered deltas. The order of deltas is semantic because dependent transactions such as create-then-add-component must replay in the same sequence.

FieldPolicy
format_versionRequired. Readers reject unsupported major versions instead of guessing.
library_versionDiagnostic metadata only; compatibility is decided by format_version and schema keys.
recordsStores committed undo and redo records in stack order.
labelOptional UI metadata. It must not affect replay semantics.
deltasOrdered logical deltas with explicit variant tags and typed payload fields.

Identity

Entity identity must be stored as index + generation, matching the runtime restoration policy where undoing a destroy restores the same EntityId. Component identity needs a stronger rule: ComponentTypeId.index is session-local and must not be the only persisted key.

IdentitySerialization policy
EntityPersist index and generation. Import validates that the target world can reserve or restore those ids.
Built-in componentPersist a stable builtin name such as Transform3D, ChildOf, GlobalTransform, or Camera.
User CPU componentRequire registration with register_cpu_component_with_identity, using an application-provided stable key plus schema version or hash. Replay is rejected when the registered component does not match.
Component indexMay be cached as a local hint, but cannot be authoritative across sessions.

Payloads

User CPU components are byte-exact payloads. Their before/after bytes are safe to persist only together with a matching component schema key. Import validation resolves the registered component by component_by_stable_key and uses component_matches_identity; specified schema version/hash fields must match, while unspecified schema fields are treated as wildcards. If the schema changed, import rejects those deltas rather than reinterpreting bytes.

Blob-backed builtins do not persist CPU ref bytes as the source of truth. GlobalTransform persists its logical matrix row and format metadata. Camera persists the logical camera GPU row payload and camera metadata needed by the runtime helper. On import, the world allocates fresh blob rows and writes those payloads, producing valid CPU ref components for the current session.

Archive Export

The current export API returns retained records in stack order with the next undo or redo operation first. It first runs the same eligibility checks as undo_serialization_report / redo_serialization_report; if any record is not serializable, export returns None / null and does not mutate history diagnostics or stacks.

DeltaExported payload
entity_createdEntity id only.
entity_destroyedEntity id plus stable component identities and copied component bytes.
component_addedStable component identity and after bytes.
component_removedStable component identity and before bytes.
component_changedStable component identity plus before and after bytes.
global_transform_changedStable builtin identity, logical row bytes, and global_transform_format code.
camera_changedStable builtin identity and logical camera row bytes. There is no GlobalTransform format field.

Archive Import

Import consumes the same in-memory archive shape and replaces only the target stack. It does not append to existing records and does not clear the opposite stack. The target world must already be in the current state represented by the archive; import validates the full stack against that world before replacing anything. Only a successful import replaces the target stack; failed imports leave the target stack and world unchanged.

The validation report APIs run the same archive conversion and full-stack applicability checks without changing history stacks, the world, or last_diagnostic. Top-level, record-level, and delta-level reports expose valid, reason, and archive-order indexes. Record index 0 is the next imported undo or redo operation; delta indexes refer to the original archive order even when undo validation checks deltas in reverse application order. When full-stack validation fails, such as when an entity or component is missing from the current world or the world has drifted from the archive state, the failing delta and any later unvalidated record or delta reports are marked invalid with import_validation_failed.

FailureDiagnostic
Unsupported format_versionimport_unsupported_format

JSON Archive v1

encodeHistoryExportJson converts a TypeScript HistoryExport into a JSON string, and decodeHistoryExportJson validates that JSON string and returns a HistoryExport that can be passed to importUndoStack or importRedoStack. The JSON helpers preserve builtin logical payloads too, including GlobalTransform row bytes with global_transform_format and Camera row bytes.

The JSON decoder is the wire-shape gate: it rejects malformed JSON, unsupported archive versions, missing required fields, unsupported delta kinds, invalid base64, and mismatched record or delta counts. Import validation remains the world-aware gate; it resolves component identity, validates payload applicability against the current world, and leaves the world, stacks, and last_diagnostic unchanged for dry-run validation.

FieldJSON policy
NamingArchive fields use snake_case, such as format_version, record_count, delta_count, local_component, and global_transform_format.
EntityStored as { index, generation }.
ComponentStored as { index } only as a local hint beside stable component identity metadata.
BytesStored as bytes_base64. Number-array byte payloads are not emitted or accepted by the MVP decoder.
ValidationThe decoder rejects unsupported versions, invalid JSON shape, unsupported delta kinds, invalid base64, and mismatched record/delta counts by throwing Error.

Compatibility Policy

The v1 JSON compatibility surface is format_version = 1, snake_case field names, supported delta kind strings, entity identity fields, component identity fields, bytes_base64 payload encoding, and builtin payload fields such as global_transform_format. Adding a JSON field or delta kind requires updating the decoder, golden fixtures, invalid fixture coverage, and this document in the same change.

The in-memory archive objects are the MoonBit and TypeScript API shape for the current build. They are not a file ABI: MoonBit enum layout, object layout, internal variant names, and local component indexes may change as long as the v1 JSON compatibility surface and import validation rules remain intact.

Replay Validation

Import and replay apply the same defensive posture as runtime undo/redo: validate each record before applying it, reject stale or schema-mismatched deltas, and leave stacks unchanged when validation fails. Byte budgets and record count limits remain runtime retention policy; they do not define archive compatibility.

undo_serialization_report and redo_serialization_report are dry-run diagnostics for the retained in-memory stacks. They do not export payload bytes or define the JSON wire format. Each report includes every record and delta, marks whether it is serializable, and explains failures such as missing_stable_component_identity or unknown_component so editors can show which components need stable identity metadata before export is attempted.

Maintenance

When changing archive semantics, update the in-memory export/import tests, TypeScript JSON helper tests, v1 golden or invalid fixtures, fixture manifest audit, and this document together. Adding or removing a history fixture must update the manifest in world-history-serialization.test.ts so unclassified fixtures fail CI. If a change intentionally breaks the JSON compatibility surface, bump format_version and keep readers rejecting unsupported versions explicitly.

Out Of Scope For V1

  • Renderer mesh/material objects, GPU buffers, and device resources.
  • Asset lifetime and external resource handles referenced by ECS component bytes.
  • Collaborative editing merge, conflict resolution, or operation transforms.
  • Cross-engine-version replay beyond the explicit format_version compatibility policy.
  • Serialization of open transactions. Only committed undo/redo records are candidates for persistence.
