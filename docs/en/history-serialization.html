History Serialization

This document defines the intended persistence boundary for future WorldHistory export/import work. The current implementation keeps undo/redo records in memory only.

Status

  • WorldHistory does not currently expose a serialized history API.
  • undo_summary and redo_summary are diagnostic views for retained in-memory records. They are not a serialized history archive or compatibility format.
  • Future persistence must use an explicit history format with a format_version; MoonBit enum layout, object layout, and internal variant names are not a stable file ABI.
  • The serialized form is for editor/session persistence, not for replaying arbitrary runtime simulation or GPU resource state.

Record Shape

A future history archive should store undo and redo stacks as ordered records. Each record should contain a label, record-level metadata, and ordered deltas. The order of deltas is semantic because dependent transactions such as create-then-add-component must replay in the same sequence.

FieldPolicy
format_versionRequired. Readers reject unsupported major versions instead of guessing.
library_versionDiagnostic metadata only; compatibility is decided by format_version and schema keys.
recordsStores committed undo and redo records in stack order.
labelOptional UI metadata. It must not affect replay semantics.
deltasOrdered logical deltas with explicit variant tags and typed payload fields.

Identity

Entity identity must be stored as index + generation, matching the runtime restoration policy where undoing a destroy restores the same EntityId. Component identity needs a stronger rule: ComponentTypeId.index is session-local and must not be the only persisted key.

IdentitySerialization policy
EntityPersist index and generation. Import validates that the target world can reserve or restore those ids.
Built-in componentPersist a stable builtin name such as Transform3D, ChildOf, GlobalTransform, or Camera.
User CPU componentRequire registration with register_cpu_component_with_identity, using an application-provided stable key plus schema version or hash. Replay is rejected when the registered component does not match.
Component indexMay be cached as a local hint, but cannot be authoritative across sessions.

Payloads

User CPU components are byte-exact payloads. Their before/after bytes are safe to persist only together with a matching component schema key. Import validation resolves the registered component by component_by_stable_key and uses component_matches_identity; specified schema version/hash fields must match, while unspecified schema fields are treated as wildcards. If the schema changed, import should reject those deltas rather than reinterpret bytes.

Blob-backed builtins must not persist CPU ref bytes as the source of truth. GlobalTransform should persist its logical matrix row and format metadata. Camera should persist the logical camera GPU row payload and camera metadata needed by the runtime helper. On import, the world allocates fresh blob rows and writes those payloads, producing valid CPU ref components for the current session.

Replay Validation

Import and replay should apply the same defensive posture as runtime undo/redo: validate each record before applying it, reject stale or schema-mismatched deltas, and leave stacks unchanged when validation fails. Byte budgets and record count limits remain runtime retention policy; they do not define archive compatibility.

Out Of Scope For V1

  • Renderer mesh/material objects, GPU buffers, and device resources.
  • Asset lifetime and external resource handles referenced by ECS component bytes.
  • Collaborative editing merge, conflict resolution, or operation transforms.
  • Cross-engine-version replay beyond the explicit format_version compatibility policy.
  • Serialization of open transactions. Only committed undo/redo records are candidates for persistence.
